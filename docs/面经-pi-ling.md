> §源码证据索引。诚实边界原则：本项目（pi-ling）当前未实现的成熟能力，已明确归属同一

## 1. 项目简介（简历可用）

一个通过 Electron + React + TypeScript 独立的 Coding Agent 产品工作台。核心不是“写一个
agent 内核”，而是**把多个现成 agent 内核收敛到一套可插拔运行时架构和一套权威事实源下**：
UI 持有同一份事件日志，会话、代码修改、审批、恢复、评测能力在内核间保持一致。

一句话给面试官：**“我做的不是再造一个 agent，而是让 agent 内核变成可插拔的，并让它们
共享同一套事实与安全边界。”**

## 2. 简历 Bullet（4-5 条，以通用支柱名开头）

### 支柱一：可插拔运行时内核统一

> **可插拔运行时内核统一：** 针对单一 agent 内核耦合在业务会话里、难以替换与对照的问题，
> 抽象统一运行时接口并显式声明各内核能力，将 Native（自研核 + pi-agent）、DSH（ACP
> sidecar）、Claude Agent SDK 三套实现收敛到同一 `RuntimeAdapter`，产品会话可在完整消息
> 边界原地切换内核，失败自动回滚，使换内核不再影响聊天、审批、权限与 UI 语义。
>
> 约束：仅注册 DeepSeek 与 Anthropic 两家模型 Provider，不加载全量 Provider；切换只在 idle
> 或完整 Turn 边界允许。

### 支柱二：权威事实源与事件模型投影

> **权威事实源与事件投影：** 针对多内核各自持久化导致事实分叉的问题，只维护一套 versioned
> Session Event Log 作为唯一事实源，聊天时间线、运行活动与评测均由它只读投影，不各自维护
> 独立事实；流式 delta 先进入主窗口合并缓冲、仅在完整语义边界落盘，保证持久化与渲染一致。
>
> 约束：投影可版本化、不破坏原始事件；事件统一携带 session/run/turn/message/toolCall 与会话
> 内单调 seq。

### 支柱三：崩溃可恢复的幂等状态机

> **崩溃可恢复的幂等状态机：** 针对进程崩溃后恢复可能重复执行工具或重复调用模型的问题，
> 以 run checkpoint 记录启停/流式/待审批/待执行/执行中/轮间/终态多阶段状态，恢复时按状态
> 幂等推进：已有完成标记的工具不重执行、仅有开始无结果标记 crashed、待审批请求先查事件日志
> 是否已存在再重发，最大程度避免副作用重放。

### 支柱四：跨内核历史注入与共享（桥接）

> **跨内核历史注入与共享：** 针对外部内核不接受任意历史种子、无法直接继承共享上下文的问题，
> 向侧载进程注入桥接插件，将标准历史转换为目标内核的事件序列实现全量种子注入，并按同步
> 水位以增量模式追平新增历史；真实模型验证确认导入历史可被下一轮引用，使换内核后上下文
> 不丢。

### 支柱五：长上下文治理与行为回归评测

> **长上下文治理与行为回归评测：** 针对长对话上下文膨胀与 Agent 行为不确定、缺少客观质量
> 度量的问题，引入基于用量估计的上下文压缩（超出阈值才折叠历史、失败时回退完整历史），并
> 构建任务级评测：每项任务自带可判定的验收命令与修改边界，跑在隔离工作区，用基线对照与
> 重复次数做配对对比，支持通过率与单任务工具调用、验证次数的 A/B 度量。
>
> 诚实边界：以上两者为同一产品线的成熟能力（公开仓库可验证），本项目规划对齐、不是本项目
> 当前已完成的实现；本策略是治理与评测，不使用 LLM 作主要判定，避免引入第二个不确定变量。

### 3.2 主问与追问口播（第一人称）

**Q1（为什么做可插拔运行时）**

> 最初是单一内核直接耦合在业务会话里，UI 和事件都贴着某个 agent 的实现写。产品的聊天、
> 审批、任务、安全边界都依赖某种特定内核，当我想换成别的 agent 引擎时，要么重写一遍产品
> 层，要么把新内核的私有事件硬塞进 UI。归因是把“内核事件”和“产品事实”绑死在一起了。所以
> 我从产品层抽出一条运行时接口，三套内核分别实现它，并显式声明各自能力，产品层只认接口。
> 结果是换内核变成“实现一个适配器”而不是“重写产品”。代价是统一接口要覆盖三套内核的差异，
> 有些能力做不到一致，我就用能力声明让 UI 按各自能力渲染，而不是默认一样。

**Q2（怎么解决事实分叉）**

> 多内核各自有持久化，如果产品层也各存一份消息和状态，同一个 run 就会出现两份互相矛盾
> 的事实。归因是产品没有单一事实源。我让产品只依赖一份版本化事件日志，聊天时间线、运行
> 活动、评测都通过只读投影从它导出。运行时自己的 transcript 只作为可重建的恢复投影，
> 不作为产品事实。投影可版本化且不破坏原始事件，所以引入新的投影不会让旧数据失效。
> 结果是 UI 看到的永远来自同一份事件，不会出现“改了这里、那边没跟上”的分叉。难点是投影
> 和增量要幂等，否则重复推送会重复渲染。

**Q3（崩溃恢复为什么不重试整轮）**

> 直观做法是崩溃后重跑一遍这轮。但工具调用有副作用，（比如文件写入/执行命令），重跑会
> 重复执行；模型调用也有成本。归因是缺“这轮哪些已经发生”的持久化。我用 run checkpoint
> 记录当前阶段（启动、流式、待审批、待执行、执行中、轮间、终态），恢复时逐步判定：已写
> 完成标记的工具不再执行；只有开始没有结果的标记为 crashed 不自动重试；待审批的请求先查
> 事件日志里是否已经有这个请求，有就不再重发。结果是恢复不会重复执行工具、不会多烧模型
> 调用，只会把未完成的部分推进到一致状态。

**Q4（外部内核不接受历史种子怎么共享上下文）**

> DSH、Claude 这类内核有自己的会话持久化，我的一个内核（DSH）的对外接口不暴露任意历史
> 注入，直接告诉我它不认外部 seed。归因是标准会话协议只支持创建/恢复，不支持灌任意历史。
> 所以我往它的外侧进程注入一个桥接插件，把标准历史转换成目标内核能理解的事件序列，用它的
> 内部种子接口创建会话；切换回来后，再按同步水位用增量模式把新增历史补进去。我用真实模型
> 验证：导入一段包含特定代号的历史后，下一轮 prompt 让模型回答代号，它答出来了，证明历史
> 真的进入上下文而不是只存了文件。风险是插件要跑在隔离 sidecar 里、固定版本、用户确认。

**Q5（换内核怎么保证审批和权限一致）**

> 三套内核的审批口径如果各自实现，会出现同一操作在一个内核要问、另一个内核直接放行。
> 归因是审批规则和内核实现绑在一起。我把“一个操作该怎么分类、该不该问、为什么问”抽成
> 决策规则（按效果分类，而不是只看工具名），Native 和 DSH 共用这套规则；但“怎么门控”
> 各自实现，因为内核暴露的审批机制不同。结果是不能直接读写的工具、破坏性命令、含敏感
> 内容的写入在任何内核都会询问，产品行为一致。隔离的难点是分类要靠解析工具输入和路径，
> 防止逃逸出工作区。

**Q6（流式效果为什么不用模型的 token 流驱动）**

> 最初的做法是模型 token 增量直接推到界面渲染。它有三个问题：数据库里可能存在半条消息，
> 恢复和切换会话时要额外处理残缺状态；历史回放和实时渲染是两套代码路径；而且它依赖内核
> 提供 token 流，但我接的三个内核里 DSH 通过 ACP 拿不到 token 级流式，能力不齐。
>
> 归因是把“持久化边界”和“展示节奏”绑在了一起。我把两者拆开：完整 Assistant 消息先落
> 事件日志，界面拿到提交完成的消息后，在渲染层按短语、标点和 Markdown 代码块边界分块，
> 按剩余块数自适应间隔逐块释放。所以数据库里的内容永远完整，展示进度只是渲染层的临时
> 状态，不属于 Transcript。
>
> 收益是历史回放和实时渲染收敛成同一条路径——历史消息只是“已经播完”的消息；而且内核有
> 没有 token 流不影响产品体感，能力差异被吸收在适配层。代价是首字延迟等于整条消息的生成
> 时间，长回答会有明显等待，所以工具调用和审批必须能打断展示队列、优先显示阻塞状态。
>
> 坦白一个遗留问题：主进程里原来那套 16ms 合并的 delta 缓冲还在跑，但渲染层改造后已经
> 没有消费者，属于设计变更后没清理的死管道。我知道它在那，还没删。

**Q7（评测用什么判定标准）**

> Agent 行为不确定，同样的任务每次路径不同，不能靠人眼判对错，也不能只看它自述“做完了”。
> 归因是缺客观标准。我用任务级评测：每道题有一个可判定的验收命令，加修改文件/行数边界，
> 跑在独立工作区。判定不用 LLM，因为模型打分有随机性、贵、还引入第二个不确定变量；有客观
> 答案的任务用命令判定更稳更便宜。对开放类任务，我把评分器做成可插拔并接 LLM 打分，但
> 让它“只打分不判死”，verify 定底线。我还先用自己的标准答案驱动把评分器跑绿，再跑真
> Agent，避免测出来的失败其实是测不到的问题。

**Q8（上下文压缩失败怎么办）**

> 压缩是把长历史折叠成摘要再进入模型上下文。若摘要调模型失败，我不能让这轮对话因此跑不
> 起来。归因是压缩成了“必须成功”的硬依赖。我的策略是压缩是尽力而为：低于阈值、没有可折叠
> 内容或摘要失败都视为“不压缩”，回落成发送完整历史。所以压缩失败的最坏结果就是退回原来的
> 完整历史行为，不会让一轮对话失败。这也是“步骤失败不能连累主任务”的原则在压缩上的体现。

**Q9（多内核如何切换）**

> 我按会话记录当前用哪个内核。切换只允许在没有活跃任务、且在完整 token/轮次边界时进行。
> 切换时先安全关闭旧内核，再激活新内核，失败则回滚保持旧内核和旧时间线。切换的目标内核
> 从同一份标准消息投影拿它缺的历史；不同的历史注入策略不同（一个全量种子、一个原生恢复+上下文注入）。新内核的原生会话 id 只是内部映射，产品会话 id 保持不变，所以用户看到的是
> 同一个对话换了引擎。

**Q10（怎么验证导入历史真的被模型用了）**

> 不能只验证“文件写进去”，要验证“下一轮请求能看到”。我构造一段历史，里面埋一个只有
> 导入历史里才有的特殊代号，然后开一个新会话导入、用真实模型发一条引用了这段历史的问题，
> 看模型回答是否包含那个代号。结果模型正确答出，证明历史进入了模型上下文。这是最有力的
> 一条真实性验证，比只看“数据库有记录”强得多。
